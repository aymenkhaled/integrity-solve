2. Transaction/CDD Wizard
Create a guided transaction wizard that can be reached from the customer flow or customer detail page.

The wizard must ask:

What designated service is being provided?
Who is the service being provided for?
individual
company
trust
beneficial owner/controller
Is the customer new or existing?
Are beneficial owners known?
Are there risk triggers?
PEP
adverse media
high-risk jurisdiction
complex ownership
source of funds/source of wealth required
What checks are recommended?
Is approval/escalation required?
Routing rules:

Individual or beneficial owner -> recommend identity/KYC + AML screening.
Company or trust -> recommend KYB + company AML.
Unknown beneficial owners or complex ownership -> reviewer/compliance review.
PEP, adverse media, high-risk jurisdiction, or SOF/SOW required -> reviewer/compliance review.
Two or more risk triggers -> high risk.
One risk trigger -> medium risk.
No risk triggers -> low risk / standard CDD.
Acceptance:

User can complete the wizard.
Wizard output clearly shows recommended checks and approval path.
Wizard output is stored against the customer/case using existing schema where practical.
Wizard actions create audit entries.
3. Didit Session Creation
Add a backend route for creating a Didit verification session.

Preferred route:

POST /api/providers/didit/session

Request should include:

customer ID
capability
optional beneficial owner/person ID if applicable
reason
Required logic:

Validate workspace/customer ownership.
Create or reuse a check request.
Set vendor_data or equivalent metadata to the internal check request ID.
In DIDIT_MODE=mock, return a fake hosted verification URL and mock provider reference.
In sandbox/live, call Didit session creation endpoint using configured workflow ID.
Use KYC workflow ID for identity/KYC/AML individual flows.
Use KYB workflow ID for company/KYB flows.
Write audit log.
Acceptance:

In mock mode, the route works without Didit credentials.
A check request/result trace can be seen from customer detail.
Duplicate session creation for the same customer/capability should not create accidental duplicate billable checks.
4. Didit Webhook Handling
Add a backend route:

POST /api/providers/didit/webhook

Required logic:

Verify Didit webhook signature pattern.
Try X-Signature-V2 first.
Fall back to X-Signature-Simple.
Reject stale timestamps older than 5 minutes outside mock/local mode.
Deduplicate webhook events using a provider event ID/session ID.
Return HTTP 200 no-op for duplicate webhooks.
Map Didit session/provider reference back to internal check request using vendor_data or session/provider reference.
Normalize status into existing check result/status model.
Store raw payload in existing webhookEvents or check result structures.
Write audit log.
Acceptance:

Valid mock webhook updates a check result.
Duplicate webhook does not create duplicate result.
Invalid signature is rejected outside mock mode.
Unmapped webhook is stored or safely acknowledged without corrupting data.
