# Part 1 — Architecture & Stack Decision

## 1.1 Why This Stack
The chosen stack is optimised for a workflow-heavy, multi-tenant compliance SaaS. Every decision favours auditability, modularity, and the ability to swap provider adapters without touching core business logic.

Layer
Choice
Why
Frontend Framework
Next.js 14 (App Router)
Server Components for initial load speed; Client Components for wizard interactivity; file-based routing maps cleanly to portal structure; built-in API routes for BFF patterns.
UI Component System
shadcn/ui + Tailwind CSS
Enterprise-grade accessible components; no vendor lock-in; works perfectly with Radix primitives; easily themed for Integrity Solve brand.
Frontend State
Zustand + React Query (TanStack)
Zustand for wizard/session state; React Query for server state caching, optimistic updates, and background refetch.
Backend Framework
NestJS (TypeScript)
Decorators for RBAC guards; modular services; built-in DI container; excellent for building provider adapters; clear separation of concerns.
ORM / Database
Prisma + PostgreSQL 15
Type-safe queries; migration system; row-level security compatible; JSON columns for flexible form data alongside relational columns for reporting.
Auth
Clerk (recommended) or custom JWT
Clerk handles multi-workspace invitations, MFA, session management out of the box. Custom JWT is a fallback if client needs full data sovereignty.
File Storage
AWS S3 / Cloudflare R2
R2 preferred for cost (no egress fees); signed URLs for secure downloads; lifecycle policies for retention compliance.
Background Jobs
BullMQ + Redis (Upstash for managed)
Document generation, provider polling, webhook retry, scheduled reviews, billing sync — all need reliable queues with retry logic.
Document Generation
docx (Node) + LibreOffice/PDF conversion
Server-side DOCX from structured data; convert to PDF for viewing. Deterministic and reproducible from data snapshots.
Billing
Stripe
Subscriptions + metered usage events; Stripe webhooks for billing state sync; test mode for development.
Email/SMS
Resend (email) + Twilio (SMS)
Transactional emails and mobile verification. Resend has excellent Next.js integration.
Monitoring
Sentry + Pino structured logs
Error tracking; job failure alerts; audit trail integrity checks; provider timeout alerts.
Deployment
Vercel (frontend) + Railway or Fly.io (API + workers)
Vercel for zero-config Next.js; Railway for NestJS + BullMQ workers; Managed Postgres on Railway or Neon.io.


## 1.2 Multi-Tenant Model
Every database record is scoped to a workspace_id. A Prisma middleware layer enforces this automatically — no query reaches the database without a workspace filter. This prevents cross-tenant data leakage even if application logic has bugs.
Architecture Rule: The workspace_id scope check happens at the NestJS guard layer (before controllers) AND at the Prisma middleware layer (before database). Double enforcement is not optional.

## Milestone 4 — Generated Program Outputs (Weeks 6–8)
Goal: Completing the wizard triggers automatic generation of the Risk Assessment, AML/CTF Policy, and AML/CTF Procedures as versioned DOCX/PDF files. These are the primary tangible product value.


### M4 — Document Generation Architecture
The document generation engine follows a strict pipeline to ensure reproducibility and auditability:

Wizard Completion Event
  → Create ProgramVersion (snapshot of all form data)
  → Enqueue 4 generation jobs (one per document type)
  → Each job: load template → inject variables → render DOCX → convert to PDF
  → Store in S3/R2 with signed URL → update ProgramDocument record
  → Calculate checksum → store dataSnapshotJson (point-in-time immutable copy)
  → Send notification to user

## Milestone 8 — Provider API Layer (Weeks 14–17)
Goal: Real identity verification, AML screening, and KYB checks. Built through capability-based adapters so any provider can be swapped without touching business logic. Start with sandbox/mock adapters.


### M8 — Provider Adapter Pattern
Every external provider is accessed through a common interface. The UI and workflow layer never know which specific provider is being used — they request a capability.

// Provider Capability Contract (TypeScript)
interface ProviderAdapter {
  readonly capability: ProviderCapability;
  readonly providerName: string;
  createRequest(input: CheckRequestEnvelope): Promise<ProviderStartResult>;
  pollStatus(providerRequestId: string): Promise<NormalizedCheckResult>;
  normalizeResponse(raw: unknown): Promise<NormalizedCheckResult>;
  verifyWebhook(signature: string, body: Buffer): boolean;
  mapWebhookToRequestId(body: unknown): string;
}

// Provider Registry — resolves adapter by capability
class ProviderRegistry {
  resolve(capability: ProviderCapability): ProviderAdapter {
    // Looks up active provider config from DB for workspace
    // Returns correct adapter implementation
  }
}

// Check Request Flow
UI action (e.g., 'Run identity check')
  → POST /checks { capability, subjectId, workspaceId }
  → Create CheckRequest record (status: QUEUED, idempotencyKey)
  → Enqueue BullMQ job
  → Job: ProviderRegistry.resolve(capability) → adapter.createRequest()
  → Update CheckRequest (status: PROCESSING, providerRequestId)
  → Await webhook OR poll on schedule
  → Webhook/poll: adapter.normalizeResponse() → Create CheckResult
  → Create UsageEvent (billable)
  → Update CustomerFile state if required
  → Create Task if review required
  → Emit audit log

Acknowledged client must provide templates but no system for managing template versions or updates.
templateVersion field on ProgramDocument; template_maps/ directory in codebase; when template changes, old versions remain generatable from their snapshot; version comparison tool for admin.
CO appointment as workspace user
Step 5 appoints CO but no logic for linking appointment to an actual portal user account.
CO appointment form must link to an existing workspace_membership OR trigger a pending user invite. Orphan CO appointments (no linked user) block full implementation completion.
Multi-file beneficial owners
BO form captures owners but no spec for re-using a person across multiple client files (e.g., director of multiple entities).
BeneficialOwner records can be linked to a central PersonRecord. Screening results shared across linked files (with re-screen on demand). Reduces duplicate checks.
Billing before vs after setup
Open decision: 'should billing be required before setup, or only before paid checks?' — not resolved.
This plan recommends: billing is NOT required to complete implementation wizard. Billing is required ONLY for paid API checks. Clear UI messaging throughout. Stripe customer created at workspace registration.
Webhook replay attacks
Mentioned signature validation but no replay protection spec.
processed_at field on webhook_events table. Before processing: check if webhook_id already exists. If yes, return 200 (success) but do nothing. Timestamp validation: reject webhooks > 5 minutes old.
Data retention policy
Asked as open question but not answered in any document.
Configurable retention: generated documents = 7 years default; provider raw payloads = 7 years; audit logs = 7 years (regulatory requirement in AML/CTF context); customer forms = 7 years post-relationship end.
Offline / degraded mode
No mention of what happens if a critical external dependency (S3, Redis, provider) is unavailable.
Graceful degradation: forms still saveable if document generation queue is down; check requests queue if provider is down; billing checks fall back to cached status if Stripe is slow; clear user messaging for degraded features.
Suspicious Matter Report (SMR) workflow
Referenced in unusual activity matrix as 'consider reportability' but no actual SMR workflow defined.
Add Diamond-level SMR workflow: structured form for internal decision to report; confidentiality controls (restricted role access); external submission tracking (manual); SMR never visible to onboarding users.
Workspace suspension / billing past-due
billingStatus = PAST_DUE / SUSPENDED mentioned but no detail on what the UX looks like.
Past due: banner warning on all portal pages; 7-day grace period before checks are blocked; 30-day grace before full suspension. Suspended: read-only mode with clear messaging; 90-day before hard close. All states reversible by adding valid payment.
Provider sandbox vs production config
No detail on how to manage provider environment config.
ProviderConnection has environment field (SANDBOX / PRODUCTION). Per-workspace config allows workspace to be in sandbox while another is live. Switching requires explicit admin action + audit log.


## 10.2 Open Decisions from PDF — Recommended Answers
Open Decision
Recommended Answer
Which identity, KYB, AML providers?
Start with Facia (identity), ABR free API (ABN/ACN lookup), AML Watcher (AML screening) as MVP candidates. Build adapters first; swap providers without code change.
Billing required before setup?
No. Billing should only be required before paid checks are activated. Setup wizard should be completable without billing.
AML form questions final?
Form schemas must be approved by client compliance expert. This plan builds the form engine; the client fills in the content and rule weights.
Generated documents editable in portal?
No for MVP. Documents are regenerated from form updates, not directly edited. Add controlled in-portal editing as a future enhancement (Diamond layer).
Which roles mandatory in MVP?
All 6 roles are needed but REVIEWER and PROGRAM_CONTRIBUTOR can map to same user in small teams. MVP bundles COMPLIANCE_OFFICER + REVIEWER permissions by default.
Final UI designs or wireframes?
Use provided wireframes + clean SaaS design system (shadcn/ui + Tailwind). Do not over-invest in custom design before workflows are validated.
Live APIs or mocked adapters in M1?
Mock adapters for M1–M6. Real sandbox APIs from M8. Real production APIs from M10.
Export formats required?
DOCX + PDF for documents; CSV for list exports; ZIP bundle for compliance evidence packs. All formats in MVP.
Evidence and document retention?
Default 7 years (AML/CTF regulatory standard). Configurable per workspace within platform bounds. Auto-delete job with pre-deletion notification.
